# 服务启动、停止与故障

`App.Start` 先检查协议与本地注册方法，再创建宿主。项目模块按依赖顺序初始化，随后启动 Pitaya，装配的执行组也就绪后，宿主开放业务入口。一个进程只能启动一次框架网络实例。

```mermaid
flowchart LR
    Init["初始化项目资源"] --> Transport["启动 Pitaya"]
    Transport --> Ready["宿主开放业务"]
    Ready --> Stop["显式 Stop：关闭新请求入口和执行组准入"]
    Stop --> Wait["等待宿主已接收的调用，排空执行组"]
    Wait --> Exit["停止 Pitaya，按依赖逆序关闭项目模块"]
```

| 情况 | 调用方可观察到什么 |
| --- | --- |
| 自管模块初始化失败 | 启动返回错误，逆序关闭已成功初始化的模块。失败模块负责清理自己的部分初始化资源。 |
| Pitaya 启动出错并终止进程 | 清理回调可能来不及执行；修复配置或依赖后启动新进程。 |
| `App.Stop(ctx)` 等待超时 | 调用返回上下文错误并请求协作取消；后台仍等实际工作结束，再关闭后续模块。 |
| 模块 `Close` 返回错误或 panic | 宿主进入 `Faulted`，保留失败模块和未关闭的依赖。查看 `Status().PendingModules` 与返回错误。 |
| 后端失联 | 定向请求可能失败。服务发现记录的变化不会自动解除业务归属，也无法阻止失联节点的迟到写入。 |

模板用项目模块的关闭方法处理账号、玩家和 Boss 的保存与释放。玩家正常退出和 Boss 停服对保存失败的处理不同，见[状态保存](10-state-saving.md)。`App.Done()` 表示 Pitaya 的启动运行函数已经返回；需要确认整个宿主收尾时，查看 `Stop` 的结果。[宿主接入](../implementation/host-guide.md)
