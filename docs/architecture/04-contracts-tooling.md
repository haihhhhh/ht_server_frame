# 协议与配置表

## 从协议定义到业务入口

1. 在协议目录中用 Protobuf 声明消息、分组和 `service/rpc`。每个请求类型对应一个方法，响应类型可以复用。消息编号由组号和组内字段号计算。
2. 运行生成脚本得到 Go 消息类型、消息目录和语言无关的 `catalog.json`。使用 `-rpc` 可额外生成定向调用方法；使用 `-rpc -forward <服务名>` 可为该服务生成网关转发组件。项目手写实际业务方法。
3. 装配时用 `ConfigureProtocol` 将协议服务名映射到运行时服务类型，注册组件后调用 `Start`。框架检查本服务应接收的方法、路由大小写及请求和响应类型。[协议工具与命令](../../examples/protocol/README.md)

客户端按同一份目录打包数字路由，握手不下发业务映射。响应和推送都携带消息编号，请求序号只用来关联一次调用。未知数字请求返回错误，未知通知丢弃；畸形包另按格式错误处理。框架没有协议版本协商，客户端和服务端需配套发布。

## 从导表到热重载

模板使用 Luban 生成 Go 类型和 JSON，在构建时写入数据清单。运行时项目将清单、数据目录、解码和校验函数交给 `tables.Module`。服务端只读取导出结果，无需运行 Luban。

```mermaid
flowchart LR
    Load["读取清单、校验文件"] --> Decode["项目解码表、准备派生数据"]
    Decode --> Validate["校验内容及跨表关系"]
    Validate --> Publish["一次发布完整配置"]
    Publish --> Read["一次业务操作取一个快照"]
```

`Reload` 的准备或校验失败时继续使用旧配置，成功后新操作使用新版，已经取得的快照仍然有效。每个进程独立重载。运行中的业务对象是否需要更新，由项目处理。[配置表接入](../implementation/tables-guide.md)
